# Open English Translation (OET) MCP Server: Comprehensive Plan & Architecture

## Executive Summary

The **Open English Translation (OET)** is a uniquely structured, open-licensed biblical corpus consisting of two complementary parallel streams:
1. **Readers' Version (OET-RV)**: Natural, idiomatic, thought-for-thought modern English designed for discourse comprehension.
2. **Literal Version (OET-LV)**: Transparent, formal-equivalence English showing every added word, copula, untranslated particle, and original syntactic structure.
3. **Word-Level Interlinear & Lexical Graph**: Every word is linked via TSV datasets to Hebrew/Aramaic (UHB) and Greek (SR-GNT) dictionary entries, Strong's numbers, morphological tags, and gloss occurrence distributions generated by [`OpenBibleData`](https://github.com/Freely-Given-org/OpenBibleData) and [`BibleOrgSys`](https://github.com/Freely-Given-org/BibleOrgSys).

This document outlines a comprehensive architectural and implementation plan to expose the OET ecosystem through the **Model Context Protocol (MCP)** as `oet-mcp-server`.

---

## 1. Comparative Analysis: How Bibles Are Made Available to AI

| Approach | Typical Implementations | Strengths | Severe Limitations for AI |
| :--- | :--- | :--- | :--- |
| **Flat Text APIs** | API.Bible, ESV API, Bible Gateway, Bolls Life | Easy to implement; fast lookup of raw verse strings. | **Zero grammatical depth**. The LLM must hallucinate Hebrew/Greek roots; cannot explain translation divergence; loses discourse structure and metadata. |
| **Traditional Interlinear Web Portals** | STEPBible, Blue Letter Bible, BibleHub | Rich human-facing lexicons and Strong's data. | **UI-centric, not agent-centric**. HTML scraping required; massive token payloads choke context windows; lacks structured JSON/diff outputs. |
| **Standard Bible MCP Servers** | Generic `bible-mcp` tools | Simple tool calls (`get_verse`, `search_bible`). | **Single translation bias**. Treats Scripture as homogeneous flat text; cannot explore translation philosophy or original language nuances. |
| **OET MCP Server (Proposed)** | `oet-mcp-server` (FastMCP + Embedded SQLite/DuckDB) | **Dual-stream parallel exegesis** (RV + LV side-by-side); **word-level token graph**; **morphological & lexical lookup**; **deterministic translation diffs**. | Highly optimized token payloads, multi-tier granularity (Doc $\rightarrow$ Sec $\rightarrow$ Verse $\rightarrow$ Word $\rightarrow$ Lemma), zero API key requirements, fully local/offline capable. |

## 3. Data Schema & Ingestion (OpenBibleData Integration)

The server relies on an embedded SQLite database (`oet_corpus.db`, ~25–45 MB) pre-compiled or auto-downloaded on first run.

### Core Tables

1. **`books`**:
   * `book_code` (e.g., `JHN`, `GEN`), `testament` (`OT`/`NT`), `canonical_order`, `name`, `full_name`, `chapters_count`, `sections_count`.
2. **`sections`**:
   * `section_id` (e.g., `JHN_S2`), `book_code`, `section_number`, `heading`, `start_ref` (`JHN 1:1`), `end_ref` (`JHN 1:18`), `parallel_refs`.
3. **`verses`**:
   * `verse_id` (`JHN.1.1`), `book_code`, `chapter`, `verse`, `rv_text`, `lv_text`, `has_missing_verse_flag` (`◘`), `poetry_parallel_flag` (`≈`).
4. **`words`** (The core word-linking table):
   * `word_link_id` (`JHNc1v1w5` / `#62342`), `book_code`, `chapter`, `verse`, `word_seq`, `surface_form` (`λόγος`), `transliteration` (`logos`), `original_lang` (`greek`/`hebrew`), `lemma` (`logos`), `strongs` (`G30560`), `morph_code` (`N-NMS`), `part_of_speech` (`noun`), `case_val`, `gender`, `number`, `tense`, `voice`, `mood`, `lv_gloss` (`message`), `rv_gloss` (`message`), `markup_tags` (`addArticle`, `untr`, `addCopula`, `nominaSacra`, `wj`).
5. **`lexicon`**:
   * `lemma_id`, `lang`, `lemma`, `transliteration`, `strongs`, `primary_gloss`, `definition_md`, `total_occurrences`, `gloss_distribution_json` (e.g., `{"message": 50, "saying": 5, "speech": 4, "statement": 4}`).
6. **`notes_and_xrefs`**:
   * `note_id`, `verse_id`, `note_type` (`footnote_rv`, `footnote_lv`, `xref`, `translator_note`), `caller_text`, `note_content`.

## 4. MCP Interface Specification

### 4.1. Resources & Resource Templates

| URI Pattern | Description | Returned Payload |
| :--- | :--- | :--- |
| `oet://catalog` | Lists all books, testaments, chapter counts, section outlines. | JSON / Markdown Catalog |
| `oet://metadata/rv` | Translation philosophy and formatting rules for OET-RV. | Markdown Documentation |
| `oet://metadata/lv` | Markup explanation for OET-LV (`addCopula`, `untr`, etc.). | Markdown Documentation |
| `oet://passage/{version}/{ref}` | Direct read access to any passage (`rv`, `lv`, `parallel`, `interlinear`). | Clean Structured Markdown |
| `oet://section/{section_id}` | Retrieve pericope / section (e.g., `JHN_S2`). | Section verses + headings |
| `oet://word/{word_id}` | Retrieve single word-link entry with morphology and glosses. | Word metadata JSON |
| `oet://lexicon/{lang}/{id}` | Retrieve dictionary entry by lemma or Strong's ID. | Lexicon entry Markdown |

### 4.2. Tools (Executable Functionality)

#### 1. `get_passage`
* **Parameters**:
  * `reference` (*string*, required): Standard Scripture reference (e.g. `"John 1:1-5"`, `"Gen 1:1"`, `"Rom 8"`).
  * `version` (*enum*: `"parallel"`, `"rv"`, `"lv"`, `"interlinear"`, default: `"parallel"`).
  * `include_notes` (*bool*, default: `true`): Include translator footnotes (`TD:`, `TC:`, `Hist:`, `Fig:`) and cross-references.
  * `format` (*enum*: `"markdown"`, `"json"`, default: `"markdown"`).
  * `show_decision_codes` (*bool*, default: `false`): Reveal inline decision tags (`[@referent]`, `[≈rewording]`, `[+the]`).
* **AI Benefit**: Gives the LLM clean, token-efficient side-by-side or individual text without formatting noise.

#### 2. `compare_translations`
* **Parameters**:
  * `reference` (*string*, required): Verse or passage reference.
* **AI Benefit**: Returns a granular comparison diff between RV and LV:
  * Highlights added words in LV (`[the]`, `[is]`, `[it]`, `[things]`).
  * Highlights untranslated particles in LV (`{the}`, `{DOM}`).
  * Isolates explicit RV translation decisions (`@` referents, `≈` rewordings, `#` number changes, `%` person shifts, `^` opposite phrasing, `?` uncertainties).
  * Notes discourse clause order swapping (`⇔`) and Hebrew poetic parallelism (`≈`, `^`, `→`).

#### 3. `get_translation_decisions`
* **Parameters**:
  * `reference` (*string*, required): Scripture reference.
* **AI Benefit**: Isolates and lists all explicit `\add` decision codes and rationale in the specified passage.

#### 4. `search_lemma`
* **Parameters**:
  * `lemma_or_strongs` (*string*, required): Hebrew/Greek lemma (e.g., `"logos"`, `"agape"`, `"bereshit"`) or Strong's ID (`"G3056"`, `"H7225"`).
  * `testament` (*enum*: `"all"`, `"OT"`, `"NT"`, default: `"all"`).
  * `limit` (*int*, default: `30`).
* **AI Benefit**: Prevents LLM hallucinations during biblical word studies. Returns exact count and distribution of English glosses used across RV and LV for that original word.

#### 5. `lookup_word`
* **Parameters**:
  * `word_id` (*string*, required): e.g. `"JHNc1v1w5"`, `"MAT_1:1w1"`, `"GEN_1:1w1"`.
* **AI Benefit**: Direct drill-down into a specific word occurrence: grammatical parsing, original leaf collation link (SR-GNT/UHB), Strong's number, and gloss context.

#### 6. `get_lexicon_entry`
* **Parameters**:
  * `query` (*string*, required): e.g., `"G3056"` or `"logos"`.
  * `lang` (*enum*: `"greek"`, `"hebrew"`, `"auto"`, default: `"auto"`).
* **AI Benefit**: Fetches comprehensive dictionary definition, semantic range, etymology, and canonical distribution.

#### 7. `search_text`
* **Parameters**:
  * `query` (*string*, required): Keywords or phrases.
  * `version` (*enum*: `"both"`, `"rv"`, `"lv"`, default: `"both"`).
  * `testament` (*enum*: `"all"`, `"OT"`, `"NT"`, default: `"all"`).
  * `limit` (*int*, default: `20`).
* **AI Benefit**: High-speed full-text search powered by SQLite FTS5.

### 4.3. Prompts (Pre-Engineered Agent Workflows)

#### 1. `comparative_exegesis`
* **Arguments**: `passage` (e.g., `"John 1:1-18"`, `"Romans 1:16-17"`)
* **Workflow**:
  1. Calls `get_passage(reference=passage, version="parallel")`.
  2. Prompts the agent to examine macro-level themes via **OET-RV**.
  3. Prompts the agent to check grammatical structure and added words via **OET-LV**.
  4. Calls `search_lemma` on key theological terms to contextualize their canonical usage.
  5. Produces a rigorous, balanced exegetical summary.

#### 2. `biblical_word_study`
* **Arguments**: `lemma_or_strongs` (e.g., `"G4102"` or `"pistis"`)
* **Workflow**:
  1. Calls `get_lexicon_entry` for primary definition and semantic domain.
  2. Calls `search_lemma` to inspect gloss variations between RV and LV across different biblical genres.
  3. Synthesizes a word study explaining how the OET renders the term across varied contexts.

## 7. Sample AI User Interactions

### Scenario 1: Explaining Translation Choices
* **User**: *"Why does John 1:1 in the OET use 'message' instead of 'Word'?"*
* **Agent Actions**:
  1. Calls `oet://passage/parallel/JHN.1.1` $\rightarrow$ inspects RV and LV renderings.
  2. Calls `lookup_word("JHNc1v1w5")` $\rightarrow$ inspects lemma `logos`, Strong's `G30560`, and translation notes.
  3. Calls `search_lemma("logos")` $\rightarrow$ notes that `logos` is translated as "message" in 50 instances, "saying" in 5, "speech" in 4.
* **Agent Response**: Cites the exact lexical data, Strong's concordance statistics, and translation philosophy directly from the OET notes without hallucinating.

### Scenario 2: Comprehensive Comparative Exegesis
* **User**: *"Run a comparative exegesis on Romans 1:16-17."*
* **Agent Actions**:
  1. Executes `comparative_exegesis(passage="Romans 1:16-17")`.
  2. Synthesizes discourse flow from OET-RV, identifies syntactical emphasis and added referents in OET-LV, and analyzes underlying Greek roots (e.g. `dikaiosynē` and `pistis`).
